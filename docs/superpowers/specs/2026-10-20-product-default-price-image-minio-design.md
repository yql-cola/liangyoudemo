# 商品默认售价、主图与销售开单选品设计

日期：2026-10-20（Asia/Shanghai）  
状态：用户已要求按此设计开发；实现与本机存储验证完成，上线步骤见部署说明  
范围：商品管理、销售开单选品、商品图片存储与单机部署

## 1. 已确认的需求和边界

- 每个商品维护**一个默认售价**，不按零售/批发类型分别定价。
- 每个商品最多一张主图；商品管理可上传、替换、删除，开单选品可看缩略图及原图预览。
- 图片存储使用本机 Docker 运行的 MinIO。用户估计主机内存约 100 GB；部署前以宿主机和 Docker 实测可用内存为准。
- 默认售价只用于开单带入；店员可以修改本单单价，订单继续保存实际成交单价。旧订单的价格不受商品档案调整影响。
- 本期不做按客户、仓库、日期的价目表，不自动更新历史订单，不做多图相册或图片进入销售单打印件。

这份设计补充并覆盖 `2026-10-19-unified-sales-delivery-design.md` 中“单价继续由店员手动输入、不建设默认价”的对应段落；销售状态和库存规则不变。

## 2. 代码现状与直接影响

| 当前实现 | 设计含义 |
| --- | --- |
| `base_product` 已有 `image_url`，无售价字段；商品 CRUD、DTO、VO、Excel 导入均带图片地址 | 售价需要追加字段；保留旧图片地址的读取兼容，不重写历史值 |
| 商品表单由 `schemas.js` 驱动，`BasicDataPage.vue` 生成弹窗；图片地址是文本框 | 商品专属主图控件需在通用页面中按字段类型局部扩展，其他资料表单不变 |
| `BasicDataSelect` 共用商品 `/options` 接口，选中时返回完整 option | 扩展商品 option 的默认价和图片标识，由开单场景按需显示缩略图 |
| `SaleOrderEditor.productChanged` 只带名称、规格、基础单位；新增行单价为 `0` | 选中商品、切换业务单位时增加默认价计算；未定价与有意输入 `0` 要区分 |
| `/products/{id}/units` 返回 `convertRate`，表示该业务单位折合的基础单位数量 | 非基础单位的默认售价 = 基础单位售价 × `convertRate` |
| `SaleOutItemRequest.unitPrice` 非负、最多四位小数；订单明细有 `unit_price` 快照 | 不改销售订单表、入参和金额结算规则 |
| 商品选项允许销售人员访问，商品详情接口需要商品查看权限 | 图片读接口需要给销售订单创建/编辑及商品查看人员授权，写接口沿用商品编辑权限 |

## 3. 数据与价格语义

`base_product` 追加 `default_sale_price DECIMAL(18,4) NULL`。`NULL` 表示尚未设置；`0` 是明确的免费或赠送价格，不能混同。校验非负且最多四位小数。商品维护页面标注“基础单位默认售价”，显示基础单位名称；创建商品时可以暂不填价格，方便先建档。

商品 `ProductSaveRequest`、`ProductResponse`、`BaseProduct` 和商品选项响应增加同名 `defaultSalePrice` 字段。商品列表显示默认售价及基础单位。商品 Excel 导入模板、解析与导出增加“默认售价”列；解析器同时识别旧表头和增加新列后的表头，旧模板没有该列时按未设置处理，避免既有批量导入失败。Excel 中空值对应 `NULL`，数字 `0` 对应明确零价。

选择商品时，使用当前商品默认价带入该行；未设置则该行 `unitPrice = null`，显示“商品未设置默认售价，请填写本单单价”，提交前要求店员输入一个明确数值，允许明确输入 `0`。切换业务单位时，只对尚未被人工修改的价格重算，计算式为 `defaultSalePrice × convertRate`，以十进制计算并按四位小数四舍五入；金额继续按每行数量乘实际单价保留两位小数。若换算后超过当前单价字段范围或精度，应提示手工填写，不静默截断。

行内记录仅用于前端交互的价格来源（系统带入/人工修改）。人工修改后，切换单位或零售/批发类型都不覆盖单价；重新选择商品会清除原商品、单位、价格来源，按新商品重新带入。零售/批发切换本身不改价，因为商品只有一个默认价。编辑已有订单和复制订单保留其原实际单价；重新选择商品才取新默认价。最终请求仍提交现有 `unitPrice`，后端继续以请求中的实际价格计算和校验，不重新覆盖为商品默认价。

## 4. 图片数据与存取流程

为避免把对象路径塞入含义为 URL 的旧字段，`base_product` 追加 `image_object_key VARCHAR(255) NULL`，存私有桶中的原图对象键；缩略图使用可由原图键推导的对象键。现有 `image_url` 保留作旧外部图片地址：优先展示已上传的主图；没有托管主图时展示有效的旧地址；两者都没有时展示占位图。新管理界面以文件上传为主，不要求用户填写图片服务器地址。更换为上传图片时清除旧外部地址，删除图片时清除两种引用，防止旧图意外重新出现。更新普通商品字段时不得把既有图片引用清空。

管理操作：先保存商品档案，再对已有商品 ID 调用 `POST /api/v1/basic/products/{id}/image` 上传；`DELETE /api/v1/basic/products/{id}/image` 删除。新增商品的页面可先暂存浏览器选中的文件，基础资料保存成功后自动上传；若上传失败，商品已创建，弹窗保留并显示“图片上传失败，可重试”，不假装整单回滚。替换图片先写新对象并更新数据库引用，成功后清理旧对象；清理失败记录日志并由人工或定时清理孤儿对象。上传接口应防重复提交。

图片读接口分别提供原图与缩略图，例如 `GET /api/v1/basic/products/{id}/image` 和 `/thumbnail`。后端先校验商品可见性和权限，再从 MinIO 流式传输；前端通过已有带 JWT 的请求封装取得 Blob 并生成临时对象 URL，组件销毁或图片变化时释放 URL。商品 option 返回 `hasImage`、图片版本标识及已有的 `imageUrl` 旧地址；托管图片只走鉴权接口，旧 HTTP(S) 外部地址由浏览器直接加载，不让后端代抓取外部 URL。任何响应都不返回永久公开桶地址或 MinIO 凭据。图片读取失败显示占位与轻量错误提示，不阻塞价格带入或订单保存。

上传限制建议为 JPEG、PNG，单文件不超过 2 MiB、解码尺寸不超过约 600 万像素；校验实际文件内容及解码结果，不只信任扩展名和 `Content-Type`。生成约 160×160 的 JPEG 缩略图，处理并发受限，原图和缩略图都存 MinIO；禁止 SVG 等主动内容。对象键由服务端随机生成，不采用原文件名。商品选项下拉只对当前可见项按需加载图片，每轮搜索最多预取前 20 项且图片请求并发不超过 4；滚动到其他结果时再加载，避免一次搜索对 MinIO 发起大量请求。图片用浏览器和后端缓存头缓存，替换时依图片版本更新。

## 5. 页面交互

商品管理列表在名称附近显示小图和默认售价；详情/编辑弹窗显示图片预览、上传、替换、删除和上传状态。图片字段只对商品 schema 生效，沿用现有白色卡片、蓝色主操作、红色危险操作及局部样式。保存商品或图片失败时显示明确错误，重复点击不能发起重复上传。

开单商品下拉每项显示缩略图、商品名称、编码、规格和基础单位；无图显示占位。已选商品所在行显示约 40–48 px 缩略图，点击可看原图。没有价格的商品仍可选择，但保存前必须明确填本单价格。缩略图加载状态与商品选项加载状态分开，图片故障不影响选品。快速连续搜索或切换商品时丢弃过期响应，避免旧图落到新商品行上。

为了不改变所有 `BasicDataSelect` 使用位置，仅在销售开单传入商品图片展示开关；其他商品选择器沿用现有紧凑布局。商品选项 API 的附加字段向后兼容。选项列表现有全量返回方式在商品量较大时会带来负担；本次先仅对图片采用按需加载，如实际商品量较大，再评估商品选项分页，不擅自改变全局下拉结果语义。

## 6. 权限与接口边界

- 商品价格的创建和修改沿用 `basic:product:create/update`，无新价格权限。
- 图片上传、替换和删除需要 `basic:product:update`；创建商品后自动上传图片也要具备该权限。因此只有新增权限而无编辑权限的角色可以创建商品，但须由有编辑权限人员补图。若实际角色配置存在此情况，实施前在界面给出说明。
- 原图/缩略图读取允许 `basic:product:view/list`，以及具备 `sale:order:create/update/view` 的用户；需要在现有 `ResourcePermissionAuthorizationManager` 明确匹配图片子路径，避免被通用商品 `GET` 误判为商品详情权限。
- 桶保持私有，浏览器只访问应用 API；MinIO API 和控制台不对公网直接开放。对象键和服务凭据仅在后端及部署配置中使用。

## 7. MinIO 单机 Docker 部署

部署一台 MinIO 实例、一个持久化数据目录和一个私有商品图片桶；使用 Docker Compose 固定镜像版本或摘要、容器重启策略、健康检查、日志轮转、持久卷及环境变量凭据。API `9000` 和控制台 `9001` 默认只绑定 `127.0.0.1`；若后端也在 Docker 中，改用同一内部 Docker 网络和容器名访问，仍不对外开放。后端配置 `endpoint`、`bucket`、access key、secret key，凭据不写入 Git。给应用创建仅限商品图片桶的服务账号，不使用根账号处理日常请求。

用户估计主机内存约 100 GB，仍需核实 Docker 实际可用内存、其他服务占用及磁盘空间。初始部署给 MinIO 设置约 1 GiB 容器内存上限、受控上传并发和日志轮转；这是该小图片工作负载的**试运行配置**，不是官方最低内存保证。上线前以连续上传、检索和页面并发访问测量 RSS、重启及延迟，再调整上限。不要让图片处理把整个上传文件和原图长期留在 JVM 堆中；处理期间限制解码并发，下载采用流式传输。

MinIO 社区仓库已归档，旧二进制/镜像不再持续维护。实施时应确认可获取的源码版本，从固定源码提交构建并固定部署镜像摘要，记录构建与漏洞核验结果；不使用浮动 `latest`。这一点是运维风险，未来若需要持续安全更新，可在保持 S3 存储接口的前提下切换维护中的服务。单机 MinIO 与数据库一起备份：备份对象数据目录、商品表记录和部署密钥的恢复方式；定期验证从备份恢复图片。单机磁盘损坏不能靠 MinIO 自身恢复。版本现状依据：[MinIO 官方仓库说明](https://github.com/minio/minio/blob/master/README.md)、[官方版本记录](https://github.com/minio/minio/releases)；容器内存限制语义依据：[Docker Compose 服务配置](https://docs.docker.com/reference/compose-file/services/)。

## 8. SQL、上线顺序和兼容

1. 对现有数据库，只在 `sql/update.sql` 末尾追加带 Asia/Shanghai 时间、原因、影响对象、执行顺序和重复执行条件的独立段落，追加两个商品字段；不改历史 SQL。具体 SQL 以实施时复核实际数据库列状态后编写。
2. 对全新环境，只在 `sql/grain_oil_ims_init.sql` 文件末尾追加相应结构变更定义，不修改原有建表段落；初始化完成后应用末尾变更。
3. 先备份数据库并执行结构变更，再部署 MinIO、建私有桶和服务账号，再部署后端，最后发布前端。现有商品价格为 `NULL`，由管理员逐步补录；旧图片地址保留展示。无需自动迁移旧图片文件，也不自动执行 SQL。
4. 如后续决定把旧外部图片批量迁入 MinIO，单独设计一次性迁移脚本与人工校验步骤，不在本次升级时隐式下载和改写历史图片。

## 9. 验收和验证范围

- 商品默认价为 `NULL`、`0`、四位小数时，表单、选项、Excel 导入和开单显示正确；非法负数或超精度被拒绝。
- 基础单位与换算单位带价正确；人工改价后切换单位和销售类型不覆盖；换商品会带入新价；编辑、复制订单保留原价。
- 上传、替换、删除、超限和伪造类型图片均有明确反馈；无图、失效旧地址、MinIO 暂时不可用时仍能选品和保存订单。
- 商品编辑者可上传；销售开单人员可看图但不可上传；无相关权限者不可读取私有图。
- 局部测试覆盖商品接口和服务、权限映射、销售表单计算及选品交互；Docker 部署后手工做上传、缩略图、原图、容器重启和备份恢复验证。

用户后续已授权依据本设计开发并运行本机 Docker MinIO。业务 SQL 仍按项目规则仅交付文件，须手动核对并执行；业务进程的环境变量、重启和页面验收见 `deploy/minio/README.md`。
