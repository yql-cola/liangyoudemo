# 登录请求头优化与现有菜单的角色授权设计

日期：2026-10-20

状态：设计已确认，待实施

适用范围：前端登录态、JWT 权限载荷、现有菜单和按钮的角色授权

## 1. 背景与目标

超级管理员登录时，`UserService.loadLoginAuthorities` 读取所有启用的权限编码，`JwtTokenService` 将这些编码写入 JWT。前端把 JWT 存入 `Liangyou-Token` Cookie，又在 API 请求中通过 `Authorization: Bearer` 发送，使同一个 Token 可能在请求头中出现两次。用户遇到 Tomcat 的 `Request header is too large`；实际超限请求的各头部字节数仍须在实施前后通过浏览器 Network 核对。

同时，现有角色页面新增角色时不能配置菜单，分配权限需要手输 ID，编辑时不能回显角色已分配的权限。`菜单权限`页只展示当前用户可见的菜单树。目标是在不引入动态路由、不建设菜单 CRUD 的前提下，让管理员以树形控件给角色配置项目已有的菜单、页面及按钮权限，并保持后端授权与前端可见性一致。

## 2. 已确认范围与现状

1. 登录态改用当前标签页的 `sessionStorage`。刷新当前标签页保留登录；新标签页不共享登录态。浏览器“恢复上次会话”可能恢复标签页存储，因此关闭标签页不等于服务端注销。
2. 只配置 `sys_permission` 中已有的菜单和权限点。前端页面仍由 `frontend/src/router/index.js` 注册；数据库中的 `path` 不用来加载任意前端组件。
3. 角色权限变更对新登录用户生效。已登录普通用户继续使用 JWT 中的权限快照，直到重新登录或 Token 到期；当前默认有效期为 7200 秒。管理页面保存成功后应提示这一规则。
4. 现有 `sys_permission`、`sys_role_permission` 及用户直接授权模型继续使用；不改变数据库表结构、现有响应字段和普通用户的权限合并规则。
5. `/api/v1/menus/tree` 仍返回当前用户可见菜单，不能直接充当角色授权目录：它只含菜单，不含按钮、接口权限，且会按当前用户过滤。

## 3. 登录态与请求头

### 3.1 前端存储

`frontend/src/utils/auth.js` 统一从 `sessionStorage` 读写 Token。登录成功后只写当前标签页存储；`frontend/src/utils/request.js` 继续只添加 `Authorization: Bearer <JWT>`。首次读取若发现旧 `Liangyou-Token` Cookie 且当前标签页尚无 Token，则先迁移到 `sessionStorage`，再删除旧 Cookie；如果两处都有 Token，以当前标签页存储为准并删除旧 Cookie。迁移不重新签发 Token，原过期时间保持不变。

主动退出、接口返回 401 时，清理当前标签页存储和旧 Cookie。主动退出仍调用后端注销接口，使当前 JWT 的 Redis 撤销标记生效；即使注销请求失败，前端也清理本地登录态。迁移逻辑不得把 Token 写回 Cookie。现有 JS 可读取 Cookie 和 `sessionStorage`，前端仍需沿用现有代码审查与输出转义要求，避免脚本注入读取凭证。

### 3.2 JWT 载荷

普通用户的 JWT、权限加载和后端鉴权规则保持现状。对 `SUPER_ADMIN`，签发 JWT 时只保留身份、角色、签发及过期时间，`permissions` 使用空列表；登录响应的 `userInfo.permissions` 仍提供全部启用权限编码。后端 `JwtAuthenticationFilter` 已根据角色生成 `ROLE_SUPER_ADMIN` authority，`ResourcePermissionAuthorizationManager` 已按该角色放行接口。旧 JWT 中带完整权限列表的情形继续按现有解析逻辑接受到过期或注销。

超级管理员访问 `/api/v1/auth/me` 时，从现有权限数据查询启用权限编码，仍返回原有 `roles` 和完整 `permissions` 字段，供路由、侧栏、按钮和页面内操作判断使用。普通用户 `/auth/me` 继续返回 JWT 权限快照。`/auth/login`、`/auth/me` 的响应字段及前端权限判断接口不变；不把超级管理员角色值直接当作前端权限数组使用。

## 4. 角色授权设计

### 4.1 授权目录与回显

新增“可分配权限树”只读查询接口，返回 `sys_permission` 的现有记录，至少包含 ID、权限编码、名称、类型、父 ID、状态和子节点。菜单、页面、按钮及现存接口权限均按父子关系展示并标明类型；这棵树只用于选择已有权限，不提供新增菜单或配置新前端路由。授权节点以权限 ID 为唯一键，父节点仅负责分组，勾选子节点不隐式授予未选中的父节点权限。树内的选择状态以实际勾选的 ID 为准，避免 Element UI 父子联动扩大授权。

新增“角色已分配权限 ID”查询接口，用于编辑和单独授权时回显。接口读取有效的角色关联，不把用户的直接授权合并到角色中。已停用权限不能新增授权；若角色原有关联已停用权限，页面须明确标识并提示，保存时按现有覆盖式授权语义将其移除，不允许静默展示为仍可使用的权限。

权限树只向具有 `system:role:grant` 的操作者提供；只拥有角色新增或编辑权限的操作者仍可维护角色资料，但不能查看或提交角色授权。超级管理员沿用现有后端角色放行规则。

### 4.2 新增、编辑与保存

角色新增和编辑弹窗展示权限树；没有 `system:role:grant` 时隐藏授权区域。角色编码、名称、状态、备注继续使用现有字段。新增角色可选择权限并一次保存；编辑角色先读取已分配权限并回显，保存时可同时更新角色资料与权限。原有“分配权限”入口保留，但改成同一棵可回显的树，不再让用户输入逗号分隔的权限 ID。

在现有角色新增、编辑请求中增加可选 `permissionIds`：

- **未传字段**：仅处理角色资料；新增角色默认无授权，编辑角色保持原授权不变，兼容原有客户端。
- **传入空数组**：需要 `system:role:grant`，表示清空该角色的授权。
- **传入非空数组**：需要 `system:role:grant`，表示用这些权限 ID 覆盖该角色的授权。

后端先对权限 ID 去重，并校验其存在且启用，再在同一数据库事务中创建或更新角色和 `sys_role_permission` 关系。任一步失败则整体回滚，不留下“角色已建但授权失败”的半成品。沿用现有逻辑删除关系的恢复方式，避免唯一键冲突。原 `POST /api/v1/roles/{id}/permissions` 保留，继续支持独立覆盖式授权。只拥有 `system:role:create` 或 `system:role:update` 的请求不得通过新字段间接获得授权能力；Service 对传入字段进行 `system:role:grant` 校验，不能只依赖按钮隐藏。

前端查询与保存显示加载状态、空数据和失败反馈；保存期间禁用重复提交。编辑回显失败时不允许提交覆盖式授权，避免把未加载到的已授权权限误清空。保存成功后刷新角色列表并提示“权限变更对已登录用户重新登录或 Token 到期后生效”。

## 5. 权限边界与数据约束

新增授权目录和角色授权回显接口应由现有 `/api/v1`、`ApiResponse`、参数校验和统一异常处理承载，并在 `ResourcePermissionAuthorizationManager` 中明确映射到 `system:role:grant`。角色新增、编辑原有 `system:role:create`、`system:role:update` 要求不变；携带 `permissionIds` 时附加检查 `system:role:grant`。`/api/v1/menus/tree` 和菜单页的只读职责不变。

用户最终权限仍按已有规则组合：有效角色权限，加用户单独授予权限，再减用户单独撤销权限。停用角色或停用权限仍不参与普通用户下次登录的有效权限计算。角色配置界面只编辑角色授权，不改用户单独授权和超级管理员身份标记。

实施前核对 `sys_permission` 的现有菜单 `path`、权限编码与静态路由及操作权限是否一致。若现有页面所需的权限记录缺失，仅把必要的数据补充 SQL 追加到 `sql/update.sql` 文件末尾，按项目要求写明时间、前置条件、执行顺序和校验方法；新环境初始化定义如需调整，也只在 `sql/grain_oil_ims_init.sql` 末尾追加。不执行迁移 SQL，不改写历史 SQL。若记录已齐全，则无需 SQL 变更。

## 6. 验收与实施边界

1. 登录后请求头仅在 `Authorization` 中携带 JWT，没有 `Liangyou-Token` Cookie；旧 Cookie 能迁移并清除。刷新当前标签页仍已登录，新标签页独立；注销或 401 清理登录态。
2. 超级管理员新 JWT 不携带完整权限列表；登录和 `/auth/me` 仍返回页面所需的完整权限。普通用户及旧 JWT 维持原有授权行为。
3. 角色新增、编辑和独立授权均能勾选已有权限并准确回显；无授权权限的操作者不能通过请求字段越权。空数组清空授权，字段缺失不改授权。
4. 创建或编辑角色与授权同事务提交，异常时回滚；停用或不存在的权限无法新授。已有菜单和按钮按授权显示，接口由后端权限规则拦截。
5. 保存角色权限后提示生效时机；已登录普通用户保持原 Token 权限直到重新登录或过期，新登录用户取得新配置。

本设计不包含菜单 CRUD、任意组件路径配置、动态路由、用户单独授权界面重做、JWT 全用户服务端化或数据库结构变更。实施时先做对应局部测试与静态检查，不默认执行全仓库测试。
